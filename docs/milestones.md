# Personal milestones (M9.1)

Milestones are authenticated, owner-scoped definitions; derived progress is recomputed from imported check-ins and is not stored as a counter. `unique_beers` and `discoveries` both count first-ever canonical `beer_id` discoveries; `checkins` counts every qualifying event, including repeats. First-ever order is the same as analytics: `occurred_at_utc`, then check-in row ID. For lifetime absolute goals `unique_beers` and `discoveries` consequently have the same value. For calendar-year and incremental goals, only beers whose first-ever imported event is within the measurement window count; repeats of beers discovered earlier never count. Brewery and style counts are not enabled: brewery IDs can be absent and style identity is name-based.

Goal types: `absolute` is lifetime cumulative; `calendar_year` selects local dates January 1 through December 31 of `calendar_year` and freezes when that year ends (`period_ended` if incomplete); `incremental` starts on inclusive `start_date` with no implicit end. Discovery always ranks against complete imported history before applying the date window. Calculations take one evaluation timestamp and exclude events later than it, so future-dated imports do not inflate progress or create future completion timestamps. A future calendar-year or incremental goal remains `scheduled` with zero progress, no completion timestamp, and no elapsed pace until its local start date. Dates use the configured IANA timezone (default `Europe/Amsterdam`); event timestamps are UTC; local date windows are half-open UTC intervals. A deadline includes its complete local day and does not stop absolute or incremental accumulation. `status` and `deadline_outcome` are separate, so late completion is retained. Completion time is reconstructed from imported event order and may predate milestone creation; historical imports, corrections, and deletions can change it.

`GET /api/v1/milestones?archived=false` returns `{ "milestones": [...] }`; `GET /{id}` returns a milestone definition plus `current`, `remaining`, `progress_percent`, status, completion, deadline outcome and available linear pace values. The compact `GET /api/v1/milestones/summary` contract returns `active_count` (active plus scheduled), `completed_count`, `overdue_count`, and up to five non-archived milestone summaries. Summary items are deterministically ordered: overdue, active, scheduled, then completed; deadline date, creation time, and ID break ties. Incomplete `period_ended` goals are omitted from the bounded items (they are not active/overdue) but progress remains available in the full list. Create example:

```json
{"active_count":1,"completed_count":0,"overdue_count":0,"milestones":[{"id":3,"name":"New beers","metric":"discoveries","goal_type":"incremental","target":100,"current":12,"remaining":88,"progress_percent":12.0,"status":"active","deadline_date":"2027-12-31","deadline_outcome":"pending","completed_at":null}]}
```

```json
{"name":"New beers in 2027","metric":"discoveries","goal_type":"calendar_year","calendar_year":2027,"target":100,"timezone":"Europe/Amsterdam","deadline_date":"2027-12-31"}
```

Use `POST /api/v1/milestones`, `PATCH /{id}`, and `DELETE /{id}`. PATCH supports `archived: true|false` to archive or unarchive. DELETE permanently removes the definition. All mutation endpoints follow existing CSRF and authenticated session requirements.

Imported history is the source of truth: older imports, deletions, and timestamp/identity corrections can change both progress and historical completion. If a source export is incomplete, historic discoveries may be misclassified until earlier records are imported. Pace is descriptive only; scheduled, completed, or lifetime goals without meaningful boundaries omit relevant values. Forecasts, management UI, dashboard insights, user administration, and audit/version history are deferred.
